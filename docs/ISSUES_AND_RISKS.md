个、`apps/shell/src-tauri/tests/move_delete_intent.rs` **8** 个，`route_for` / `trash_candidates` 的用例在 `transfer_push.rs` 模块内的 `mod tests`。**残余**（2026-11-09 复核：**「垃圾箱靠文件夹名推断」这一根因已消除**）：原来的问题不是「名字猜得不够准」，而是**结论没地方放**——协议层（`crates/xremail-protocol-imap/src/folders.rs` 的 `detect_role` / `role_from_attributes`）早就按 RFC 6154 认出了 `\Trash`，但 `folder` 表没有 role 列，同步一结束那个结论就丢了，回写删除时只能重新拿文件夹名去比 `role_by_name`。现在迁移 `crates/xremail-store/migrations/0010_folder_role.sql` 给 `folder` 加了 `role TEXT`（可空，`CHECK` 限定 `inbox`/`sent`/`drafts`/`trash`/`junk`/`archive`/`flagged`/`all`，与 `folders.rs` 实际产出一致），`xremail-sync/src/sync.rs` 把每轮 `LIST` 的 `RemoteFolder::role` **写进库**，`crates/xremail-sync/src/transfer_push.rs` 的 `trash_candidates` 按这个**降级顺序**认垃圾箱：① 库里 `role = 'trash'` 的文件夹（服务器宣告过 `\Trash`，是**事实**）→ ② 库里 `role` 为 `NULL` **且**名字命中 `role_by_name` 的（名字是**猜测**）→ ③ 都没有就就地标删，不乱挪。两条补充规则：库里角色**已知且不是** `trash`（例如服务器宣告 `\Archive`）时，名字再像垃圾箱也不算；当前文件夹自己永远排除在外（在垃圾箱里删除就是真删）。`role` 为 `NULL` 的含义被明确成「**还不知道**」而不是「没有垃圾箱」——升级上来的老库、以及服务器既没宣告属性、名字也认不出的文件夹（QQ 只给 `\NoSelect` / `\HasChildren`）都是 `NULL`；把它当否定答案的话，升级后还没同步过一轮的账户会**悄悄**从「删除 = 进垃圾箱」退化成「就地标删」，那是一次不可撤销的删除。**剩余的残余**：① 名字兜底表（`ROLE_NAMES`）仍然是手抄的三家服务商实测结果，新服务商的垃圾箱若既无属性、名字也不在表里，仍会退到就地标删（此时 `role` 保持 `NULL`，不会把猜测写成事实）；② 迁移只能加列不能改约束，`folders.rs` 以后新增角色必须同步改 `0010` 的 `CHECK`，否则写入会被数据库拒掉（这条已写进迁移注释）。**总配额与取消**仍未做（见 R09）；**发送已定义并实现**（2026-10-28：`send_queue` 六态、`uncertain` 不自动重发、冻结字节后不可改内容，见 ARCHITECTURE §5） |

## 4. 处理顺序

1. 确认 R01 的真实邮箱产品；实测 R02。无账号时可以写 mock 和只读工具，但不能宣称接入成功。
2. 固化 R03/R04 的身份、操作队列与恢复语义，再写存储和同步。
3. R06/R07 与第一条真实读信链路同时验收；不得等完整 UI 做好再补安全。
4. R08 做有限范围可行性验证，结果决定 Android 交付策略；不自动把 Android 移出目标。
5. 数据正确性通过后再测 R05/R09 的检索与性能；L2 服务、Gmail 与其他平台均不阻塞。
