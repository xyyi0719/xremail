## 1. 目标与约束

### 1.1 三条硬约束（来自产品定位与用户反馈）

1. **快**：任何操作（打开、切换、滚动、写信）不能让界面卡死或掉帧。
   已有的量化口径：滚动最长帧 < 50ms，切换邮件中位 < 100ms（见 §7）。
2. **简洁**：首屏就是邮件。设置、DKIM、授权码这类低频内容**默认不可见**。
3. **美观**：视觉规范统一——同一套 token、同一种圆角、同一种交互反馈。
   「看起来高级」的来源是**一致性**，不是更多装饰。

### 1.2 为什么选 shadcn/ui（以及它的真实代价）

shadcn/ui **不是组件库**，没有 `npm i shadcn-ui` 这种事。它是「把组件源码复制进
你的项目」的分发方式，技术栈前提是 **Tailwind CSS + Radix UI**。

真实代价（2026-11-10 实测）：只装 `@radix-ui/react-dialog` + `react-select` 两个
包，`node_modules` 就 **13 MB**；构建链要从「Vite 处理手写 CSS」变成 Tailwind。

真实收益：

* **Radix 解决的是无障碍与键盘交互**（焦点陷阱、方向键、`aria-*`）——
  这些自己写最容易漏，也最不显眼，漏了就是「感觉不专业」；
* **组件源码在仓库里**，可以改、可以删、可以为性能审计负责；
* **设计 token 是 CSS 变量**（`--background` / `--primary` / `--muted` …），
  与本项目已有的 `tokens.css` 思路完全一致——**这是无缝迁移的关键**。

**决策：引入 Tailwind v4 + shadcn/ui，但分三期，每期都有性能闸门（§6）。**
上一轮已经把 39 处硬编码颜色收敛进 `tokens.css`，命名就是 shadcn 的命名，
这一步已经在往兼容的方向走。

### 1.3 明确不做的

* **不做多主题切换器**。浅色跟随系统（`prefers-color-scheme`），深色已验证。
  主题选择器是设置负担，不是功能。
* **不做动画堆砌**。只保留 ≤120ms 的颜色过渡；列表行、面板进出**不带过渡**
  （实测过：给列表行挂 transition 会让滚动测试退化）。
* **不重写富文本编辑器**。`RichTextEditor`（458 行）是发信核心，行为已验；
  换成 TipTap 之类的库要重新验证整条发信链路，收益只有样式。

## 2. 信息架构

### 2.1 三层视图

```
┌────────────────────────────────────────────────────────────┐
│ 顶栏：应用名 · 账户切换 · 搜索 · ⚙设置 · ✉写邮件            │
├──────────┬──────────────────┬──────────────────────────────┤
│ 侧栏      │ 列表              │ 正文                          │
│          │                  │                              │
│ 收件箱 12 │ ☐ 邮件标题        │ 邮件标题                      │
│ 星标  3  │   发件人 · 摘要   │ 发件人 → 我 · 时间 · 星标      │
│ 已发送   │ ☐ ──────────     │ ─────────────────────        │
│ 草稿箱   │ ☐ 已读的邮件      │ （已消毒的 HTML / 纯文本）      │
│ 垃圾箱   │   发件人 · 摘要   │ [附件 1] [附件 2]              │
│          │                  │ [回复] [转发]                  │
├──────────┴──────────────────┴──────────────────────────────┤
│ 状态栏：上次同步时间 · 同步中…（右下角浮层：写信）              │
└────────────────────────────────────────────────────────────┘
```

### 2.2 与现状的差异（都是实测过的痛点）

| 现状 | 目标 | 为什么 |
|---|---|---|
| 设置是**页面顶部的一条 `<details>`** | 收进右侧抽屉（Sheet），顶栏一个 ⚙ 入口 | 设置打开时不应把邮件推走；抽屉即开即关 |
| 账户切换器 + 账户管理卡**分开两处** | 侧栏顶部一个**账户切换下拉**（Select/Menu），管理卡住在抽屉里 | 同一个东西出现在两个地方，用户不知道哪个生效 |
| 搜索在设置区里 | **顶栏常驻搜索框**（⌘K / Ctrl+K 聚焦） | 搜索是高频动作，藏起来就没人用 |
| 写信是右下角浮层 | **保留浮层**，但支持多封并存（Gmail 的做法） | 写信是并行任务，不该占整页 |
| 文件夹是面板卡片 | 纯文本列表（无卡片边框），未读计数右对齐 | 卡片套卡片是「不简洁」的主因 |
| 列表行自带边框和背景 | 行无边框，选中用 `--accent`，斑马纹去掉 | 边框多了就没有层次 |

### 2.3 键盘优先（Radix 的价值所在）

| 键 | 动作 |
|---|---|
| `j` / `k` 或 ↓↑ | 上下移动选中邮件（虚拟列表自动 `scrollIntoView`） |
| `Enter` / `o` | 打开当前邮件 |
| `c` | 写新邮件 |
| `r` | 回复 · `a` | 全部回复 · `f` | 转发 |
| `e` 或 `y` | 归档 |
| `#` | 删除（进垃圾箱） |
| `s` | 星标 |
| `Ctrl+K` / `⌘K` | 聚焦搜索 |
| `Esc` | 关闭最上层的浮层 / 清空选择 |

**实现要求**：快捷键在**输入框聚焦时必须失效**（`event.target` 不是
input/textarea/contenteditable）。这是邮件客户端快捷键最容易出的事故。

## 3. 设计 Token（对齐 shadcn 命名）

沿用 `tokens.css`，补齐 shadcn 组件需要的其余变量。**全部是 CSS 变量，零运行时**。

```css
:root {
  --background: oklch(100% 0 0);      /* 页面底 */
  --foreground: oklch(24% 0.01 265);  /* 正文 */
  --card: oklch(100% 0 0);            /* 面板 */
  --muted: oklch(97% 0.002 265);      /* 弱底色（选中行、hover 底） */
  --muted-foreground: oklch(52% 0.012 265);  /* 次要文字 */
  --primary: oklch(52% 0.15 255);     /* 唯一强调色 */
  --primary-foreground: oklch(99% 0 0);
  --accent: oklch(95% 0.012 255);     /* 选中行底色 */
  --border: oklch(91% 0.004 265);
  --input: oklch(89% 0.005 265);
  --ring: oklch(52% 0.15 255 / 45%);  /* 键盘焦点环 */
  --destructive: oklch(55% 0.19 25);
  --radius: 0.5rem;
}
@media (prefers-color-scheme: dark) { /* 只调 L 与 C，色相不变 */ }
```

**使用纪律**（已写进 `tokens.css` 注释，迁移时逐条执行）：

1. 组件里**禁止**出现 hex 颜色与 `rgb()`——上一轮清掉了 39 处，不能反弹；
2. **禁止** `color-mix(in srgb, currentColor …)` 做背景——深浅模式会反号
   （实测过两次：账户切换器、输入框都是这么坏的）；
3. 强调色只有 `--primary` 一个。第二强调色出现之日，就是界面变花之日；
4. `z-index` 只允许三档：浮层 20、抽屉 30、toast 40。散写会互相盖。

## 4. 组件清单（shadcn 采用哪些、跳过哪些）

### 4.1 采用（按优先级）

| shadcn 组件 | 替代现状 | 用在哪 |
|---|---|---|
| `Button` | 手写的 primary/secondary 规则 | 全部按钮 |
| `Input` / `Textarea` | `.field input` 手写样式 | 账户表单、写信、搜索 |
| `Dialog` | 无（现在用 `<details>` 冒充） | 确认删除、附件另存 |
| `Sheet` | 设置区的 `<details>` | 账户与设置抽屉 |
| `DropdownMenu` | 无 | 账户切换、邮件操作菜单 |
| `Tooltip` | `title` 属性 | 工具栏图标按钮 |
| `Toast`（sonner） | 手写的 `app-notice` | 同步完成、发信结果、错误 |
| `Skeleton` | 「加载中…」文字 | 首屏、切换账户时 |
| `ScrollArea` | 原生 `overflow`（**仅侧栏用**） | 侧栏、抽屉 |
| `Separator` | 手写边框 | 顶栏/状态栏分隔 |
| `Badge` | `.account-tag` | 服务商标签、未读计数 |
| `Empty` | `panel-empty` 文字 | 空文件夹、无草稿 |

### 4.2 不用 Radix 的（自己保留实现）

| 组件 | 为什么不用 Radix |
|---|---|
| **邮件列表** | 已有自研 `VirtualList`（48px 定高，275 DOM 节点/500 封）。Radix 没有虚拟化，引入 react-virtual 反而多一层 |
| **正文渲染** | `dangerouslySetInnerHTML` + 后端消毒，无交互组件 |
| **写邮件浮层** | 自己的 fixed 面板；Radix Dialog 的模态语义（锁滚动、焦点陷阱）对浮层**反而是错**的——写信时要能同时看列表 |

### 4.3 明确不引入

`react-window` / `react-virtual` / `framer-motion` / 任何图标库（用手写 SVG，
现有图标只有 6 个，一个库换 6 个图标不值）。

## 5. 性能设计（为什么这套 UI 不会卡）

### 5.1 已有的基础（保留，不动）

* **虚拟列表**：500 封 → 275 个 DOM 节点、18 行在屏（实测）。全渲染是 3148 节点；
* **三栏 `contain: layout paint`**：点开邮件只重绘右栏；
* **独立滚动容器**：滚动不触发整页回流；
* **行高契约**：`VirtualList.ROW_HEIGHT = 48` 与 CSS 同步，改一个必须改另一个。

### 5.2 Tailwind 之后的三个性能红线

Tailwind 带来的体积增量是**一次性的**（构建时生成），但下面三条是**每次渲染的**，
这也是三条验收闸门（§6.4）：

1. **列表行不挂过渡**。`transition-*` 只允许出现在 Button/Input；
   行的 hover 用无过渡的 `--hover` 背景。
2. **不做每帧 JS**。没有滚动监听回调、没有 IntersectionObserver 逐行挂载、
   没有 requestAnimationFrame 循环。虚拟列表的 `onScroll` 只写一个 `scrollTop`
   数字（现状如此，保持）。
3. **Radix 弹层用 `Portal` 但不常驻**。Sheet/Dialog 关闭时**卸载**子树，
   不许 `display:none` 藏着——那会让每个打开过的抽屉都留在 DOM 里。

### 5.3 体积预算

| 项 | 现状 | 引入后预算 | 超了怎么办 |
|---|---|---|---|
| CSS（gzip） | 4.7 KB | **≤ 12 KB** | 检查是否把整个 Tailwind 默认调色板都进了产物（`safelist` 清理） |
| JS（gzip） | 83 KB | **≤ 110 KB** | Radix 按需 import；检查是否误装了全量 `@radix-ui/react-*` |
| 依赖数 | 5 个 | ≤ 5 + tailwind + 用到的 radix | 每加一个都要在 PR 里说理由 |
| 首屏（列表可交互） | 155 ms / 500 封 | ≤ 250 ms | 回查是不是组件树变深了 |

## 6. 实施计划（三期，每期独立可交付、可回滚）

### 6.1 第一期：地基（1 个 PR，不改任何像素）

1. `npm i -D tailwindcss @tailwindcss/vite`（v4 是 CSS-first 配置，无 `tailwind.config.js`）；
2. `tokens.css` 的变量**原样保留**，在其上加 `@theme inline` 映射——
   Tailwind 的 `bg-background`/`text-foreground` 类就能用上现有变量；
3. 现有手写 CSS **一行不改**，只是两套并存；
4. **闸门**：构建产物 CSS gzip ≤ 12 KB、全部测试绿、截图 diff 无变化。

> 这一期结束就可以回滚：删两个依赖即可，UI 没动过。

### 6.2 第二期：骨架与低频件（1–2 个 PR）

1. **顶栏重做**：搜索常驻 + ⚙ 抽屉入口（`Sheet`）+ 账户切换（`DropdownMenu`）；
2. **设置搬进抽屉**：AccountForm / AccountList / DkimPanel / SearchPanel 原样搬，
   只换壳不换逻辑——95 条单测全部保留；
3. **侧栏改纯文本列表**：去卡片边框，未读计数用 `Badge`；
4. `Button` / `Input` / `Badge` / `Skeleton` / `Toast` 落地；
5. `app-notice` 换成 `Toast`（含深色模式回归截图）；
6. **闸门**：E2E 11 条 + 单测 95 条全绿（testid 不许改）；性能两用例不红；
   截图人工过目（浅色 + 深色各 4 张）。

### 6.3 第三期：交互升级（可选，按需）

1. **键盘导航**（§2.3 的表）；`j/k` 驱动虚拟列表的 `scrollIntoView`；
2. 写信浮层支持**多封并存**（每封一个浮层实例，右下角堆叠）；
3. `Dialog`（删除确认）、`Tooltip`、`DropdownMenu`（行内操作）；
4. **闸门**：键盘操作在输入框聚焦时失效（写一条专门的单测）；性能不红。

### 6.4 每期的自动化验收（复用现有设施）

```bash
# 全部已存在，不需要新写
npx vitest run                # 95 条（testid 不许改）
npx playwright test           # E2E + 性能 2 条 + 截图
npx vite build                # 体积预算见 §5.3
```

性能用例已经带**数字上限**（滚动 < 200ms/帧、切换 < 300ms、渲染行数 < 80），
UI 改造如果让任何一条变红，就是引入了真实的性能退化——这比「感觉卡了」可复核得多。

## 7. 基线数据（2026-11-10 实测，本机 Linux）

| 指标 | 数值 | 来源 |
|---|---|---|
| 500 封邮件 DOM 节点 | **275**（全渲染 3148） | `performance.spec.ts` |
| 渲染行数（视口 900px） | 18 | 同上 |
| 滚动最长帧 | **19.5ms**，0/684 帧超 50ms | 同上 |
| 切换邮件 | 中位 83ms / 最慢 109ms | 同上 |
| 首次打开 500 封 | 155ms | 手动测量 |
| CSS（gzip） | 4.73 KB | `vite build` |
| JS（gzip） | 83 KB | `vite build` |
| 深色模式 | 已实现并截图验证 | `04-dark.png` |

> ⚠️ **滚动用例的墙钟时长（约 12s）不是性能指标**：684 帧 × 16.7ms/帧 = 60fps
> 满帧率，12 秒是「滚完 500 行需要的重绘次数」。看最长一帧，别看总时长。
> 这个口径曾经让我误判过一次性能回归。

## 8. 风险

| 风险 | 缓解 |
|---|---|
| Tailwind v4 与 Vite 插件的版本耦合 | 第一期只加依赖不动样式，构建红就回滚 |
| Radix 组件的默认样式与现有 token 冲突 | 组件源码在仓库里，直接改类名 |
| 95 条单测按 accessible name 查找，Radix 会改 DOM 结构 | 第二期逐文件跑，红了改查询不改断言语义；**不许删测试** |
| 界面改版后 `data-testid` 丢失 → E2E 全红 | testid 是契约，迁移时保留原 testid |
| 深色模式回归（`currentColor` 反号的老坑） | 每期都出深浅两套截图，人工过目 |
| 依赖数膨胀 | §5.3 预算表，超了在 PR 里说明 |

---

## 9. 一句话总结

**第一期只铺 Tailwind 地基不动像素（可随时回滚），第二期把低频内容收进抽屉、
搜索提到顶栏（这一步用户就能感到「简洁」），第三期补键盘交互（shadcn/Radix
真正的价值所在）。** 每期都有现成的 95 + 11 条测试和带数字上限的性能用例兜底——
「快」不是感觉，是可以红的断言。

# 附：F 版实现说明（2026-11-12）

> 上面 §1–§9 是初版方案的记录。实际落地的界面与它有出入——**以本节为准**。

## F1. 最终布局

```
┌───────────────────────────────────────────────────────────────┐
│ Xremail  [me@example.com]              版本/数据目录  ⚙ 账户设置 │  顶栏
├────┬──────────────────────┬───────────────────────────────────┤
│ ✎  │ 邮件（2）             │ [归档][删除]              未读 ▾  │  阅读工具条
│ 📥 │ ┌──────────────────┐ │ 主题                              │
│ ☆  │ │ 陈静·产品   10:24 │ │ (头像) boss@example.com           │
│ ➤  │ │ Q4 预算评审安排   │ │        发给 me@example.com [标记] │
│ 📄 │ └──────────────────┘ │ ─────────────────────────────     │
│ 🗄 │ ┌──────────────────┐ │ 正文（860px 阅读列）              │
│ 🗑 │ │ 周报机器人  09:02 │ │                                   │
│    │ └──────────────────┘ │ [附件卡片]                        │
└────┴──────────────────────┴───────────────────────────────────┘
```

**三处与初版方案的关键差异**：

1. **左栏从「文字文件夹」改成 56px 图标轨** —— 初版左栏要同时放写邮件按钮、
   账户卡、文件夹列表，11–14rem 全占满，列表与正文被挤窄。
2. **列表项从「贴边行」改成「独立圆角卡片」** —— 跟随 Gmail 2026 新版
   （浅灰底 + 每封白色卡片），卡片间距 6px。
3. **账户切换移到顶栏** —— 初版把它放在设置抽屉里。重设计时一度删掉，
   E2E 抓到了「用户没法切账户」，已移到顶栏做成胶囊按钮。

## F2. 表单：一次填完

初版要「先建账户 → 再去账户卡片里单独存授权码」两步。现在**合并成一步**：

* 邮箱、服务商、**授权码**在同一屏；
* 提交时先 `create_account` 拿到账户，立刻 `save_credential` 写进平台钥匙串；
* 凭据存失败时**明确报错并提示去卡片重填**，绝不假装成功（账户已建但
  `secretRef` 为空，用户必须知道还差一步）。

另外两条相关修复：

* **服务器参数初始就预填**（默认服务商 163 的 IMAP/SMTP）。之前初始值是空串、
  只在"切换下拉"时才预填，而默认就是 163、从没切过 → 永远是空的。
* **填邮箱自动带出用户名与显示名**，且**不会覆盖用户手改过的值**。

## F3. 图标

用 **Lucide React**（`lucide-react@1.72`）。选它的理由：每个图标是独立组件、
内联 SVG、**可 tree-shake**——只打包用到的图标，不会因为引一个图标库就撑大 bundle。

映射规则（`FolderRail.tsx`）：认得出的用专用图标（收件箱/星标/已发送/草稿/
归档/垃圾箱），**用户自建文件夹统一用 `FileText`**——不按名字猜，猜错比统一更难理解。
